# Интеграционное тестирование

Два REST-сервиса для пользователей и заказов: взаимодействие сервисов в КТ-2
и интеграционное тестирование сверху вниз в КТ-5, снизу вверх в КТ-6
и гибридным методом в КТ-7. Сервис заказов получает
данные пользователя по HTTP. У каждого приложения своя H2-база в памяти.

## Структура

```text
integration-testing/
├── pom.xml
├── README.md
├── user-service/
│   ├── pom.xml
│   └── src/main/
├── order-service/
│   ├── pom.xml
│   └── src/
│       ├── main/
│       └── test/java/com/vasilevyuv/integrationtesting/orders/order/
│           ├── topdown/
│           ├── bottomup/
│           ├── hybrid/
│           └── support/
└── integration-tests/
    ├── pom.xml
    └── src/test/
```

Корневой `pom.xml` объединяет три Maven-модуля. В сервисах код разделён на предметные
модули `user` и `order`, внутри которых находятся слои:

- `api` — контроллеры, входные и выходные DTO, обработка ошибок;
- `application` — создание и получение объектов, контракт обращения к пользователям;
- `domain` — модели и контракты репозиториев;
- `infrastructure` — SQL и HTTP-клиент.

Сервисы не зависят от Java-классов друг друга и не читают чужую БД.
Имя и email пользователя добавляются в заказ при каждом HTTP-запросе.

## IntelliJ IDEA

Требования: JDK 25, Maven 3.9+; Spring Boot 4.1.1.

1. Открыть корневой `pom.xml` через **File → Open → Open as Project**.
2. Выбрать **Project SDK: JDK 25**.
3. В настройках **Build Tools → Maven** выбрать встроенный **Bundled Maven**;
   для Maven Importer и Runner указать JDK 25.
4. Выполнить **Reload All Maven Projects** в окне Maven.

Если проект уже открыт, достаточно повторно загрузить Maven-проект из корневого `pom.xml`.
В Maven должны отображаться модули `user-service`, `order-service` и `integration-tests`.
Версия IDEA должна поддерживать выбранный JDK для сборки встроенными средствами IDE;
сборка через Maven использует JDK, выбранный для Maven Runner.

## Сборка и тесты

В окне **Maven** запустить `clean verify` для корневого проекта `integration-testing`.
При первой сборке нужен доступ к Maven Central. Docker и внешний сервер БД не требуются.

При установленном Maven команда из корня репозитория:

```powershell
mvn clean verify
```

`verify` выполняет 47 проверок слоёв orders, собирает оба JAR, запускает приложения
в отдельных JVM на свободных портах и выполняет 12 межсервисных тестов.
Цель `test` выполняет только 47 проверок в `order-service`; тестам `*IT`
нужны собранные JAR и фаза `verify`.

- `ServiceApiIT`: создание и чтение пользователя и заказа, валидация, ошибки 404/422,
  пять измерений времени чтения заказа через оба сервиса.
- `UserServiceFailureIT`: остановка настоящего users, HTTP 500, неверный JSON,
  чужой ID, неполный ответ, тайм-аут и допустимая задержка.

Управляемые сбои и задержки задаются тестовым HTTP-сервером `UserServiceStub`.
Тесты останавливают запущенные ими процессы. Результаты находятся в
`order-service/target/surefire-reports/` и `integration-tests/target/failsafe-reports/`, измерения — в
`integration-tests/target/response-times.csv`. Папки `target` не входят в Git.

Проверено 30.10.2026 на встроенном Maven IDEA 3.9.8 и JDK 25:
**59 тестов, 0 неуспешных проверок, 0 ошибок, 0 пропусков; BUILD SUCCESS**.

## КТ-5 — тестирование сверху вниз

Верхняя точка входа — `OrderController`. На каждом этапе запрос проходит через
контроллер, а очередная заглушка заменяется настоящим компонентом.

| Этап | Настоящие компоненты | Заглушки | Набор |
| --- | --- | --- | --- |
| 1 | Spring MVC, контроллер, DTO, валидация, обработчик ошибок | `OrderService` | `TopDownControllerTest`, 7 проверок |
| 2 | Всё из этапа 1 и `OrderService` | `OrderRepository`, `UserDirectory` | `TopDownServiceTest`, 5 проверок |
| 3 | Всё из этапа 2, `JdbcOrderRepository`, H2 со штатной схемой | `UserDirectory` | `TopDownPersistenceTest`, 4 проверки |
| 4 | Оба приложения, HTTP-клиент, репозитории и две H2 | Нет в штатной цепочке; управляемый HTTP-сервер в отдельных сценариях отказов | `ServiceApiIT` и `UserServiceFailureIT`, 12 проверок |

На этапах 1–3 используется MockMvc: маршрутизация, JSON и валидация настоящие,
но сетевой порт не открывается. Этап 4 проверяет HTTP между отдельными JVM.
Его 12 тестов повторно используются из КТ-2, новые проверки КТ-5 — первые 16.

Для последовательного прохождения этапов выполнить из корня репозитория:

```powershell
mvn -pl order-service -Dtest=TopDownControllerTest test
mvn -pl order-service -Dtest=TopDownServiceTest test
mvn -pl order-service -Dtest=TopDownPersistenceTest test
mvn clean verify
```

Последняя команда повторяет первые три этапа и проверяет полную цепочку.
В IDEA первые три класса можно запускать зелёной кнопкой рядом с именем класса;
для `*IT` используется Maven `verify` корневого проекта.

Контроллер проверяется на ответы 201/200/404 и отклонение некорректного количества
или UUID до вызова сервиса. На втором этапе проверяются расчёт суммы, очистка
названия товара, получение актуального пользователя и запрет сохранения при
ошибке зависимости. На третьем этапе SQL-запросы подтверждают значения в H2
и отсутствие записей после ответов 422/503. Каждый тест начинает с пустой БД;
запросы не обёрнуты в откатываемую тестовую транзакцию.

Ожидаемые ответы 400/404/422/503 являются успешными негативными сценариями.
В выполненном наборе новых дефектов не обнаружено. Mockito задаёт ответы нижних
слоёв на промежуточных этапах; корректность HTTP-клиента подтверждается этапом 4.
Тесты не проверяют нагрузку и внешнюю промышленную БД: оба сервиса используют H2.

Отчёт `КТ5_Отчет.docx` и журналы запусков находятся в соседней папке `КТ5`, вне Git.

## КТ-6 — тестирование снизу вверх

Сначала проверяется хранение данных, затем к нему подключается бизнес-сервис,
после чего проверяется HTTP API. На первых двух этапах драйвером вызовов служит
JUnit-тест: он вызывает репозиторий или сервис напрямую.

| Этап | Настоящие компоненты | Точка входа и замены | Набор |
| --- | --- | --- | --- |
| 1 | `JdbcOrderRepository`, `JdbcClient`, H2 со штатной схемой | Прямые вызовы репозитория; сервис и контроллер не загружаются | `BottomUpRepositoryTest`, 7 проверок |
| 2 | `OrderService`, репозиторий, H2, `HttpUserDirectory` | Прямые вызовы сервиса; users заменён управляемым HTTP-сервером | `BottomUpServiceTest`, 5 проверок |
| 3 | Весь orders, включая контроллер и встроенный HTTP-сервер | Сетевые HTTP-запросы; users по-прежнему заменён HTTP-сервером | `BottomUpApiTest`, 5 проверок |
| 4 | Оба приложения и их H2 в отдельных JVM | Настоящие межсервисные запросы; HTTP-заглушка только в отдельных сценариях отказов | Существующие `ServiceApiIT` и `UserServiceFailureIT`, 12 проверок |

Новые тесты КТ-6 находятся в пакете `order.bottomup` и не используют Mockito или
MockMvc. `UserApiStub` заменяет только внешнее приложение: настоящий HTTP-клиент
отправляет ему запросы по сети. Журнал заглушки позволяет проверить адрес, метод
и отсутствие вызовов при отклонённом запросе или неизвестном заказе.

Последовательный запуск из корня репозитория:

```powershell
mvn -pl order-service -Dtest=BottomUpRepositoryTest test
mvn -pl order-service -Dtest=BottomUpServiceTest test
mvn -pl order-service -Dtest=BottomUpApiTest test
mvn clean verify
```

В IDEA три новых класса запускаются зелёной кнопкой рядом с именем класса.
Для проверки двух приложений используется Maven `verify` корневого проекта.
Сервисы вручную запускать не требуется; тесты выбирают свободные порты.

Первый этап проверяет SQL-маппинг, точность цены, отсутствующий ID, повторный
первичный ключ и ограничения БД на количество и цену. Второй проверяет создание
и чтение заказа через реальные JDBC и HTTP, включая запрет записи при HTTP 404/500
от users. Третий проверяет HTTP-контракт orders, валидацию до обращения к нижним
слоям и восстановление чтения сохранённого заказа после сбоя users.

На этапах 1–2 каждый тест получает новую H2 с уникальным именем; после теста БД
закрывается. На этапе 3 таблица очищается перед каждым тестом, а контекст приложения
закрывается после класса. Проверки не используют откатываемую тестовую транзакцию.

В отличие от КТ-5, контроллер подключается после проверки нижних слоёв. Новых
сценариев КТ-6 — 17; итоговая сборка также повторяет 16 проверок КТ-5 и 12 тестов КТ-2.
Отчёт `КТ6_Отчет.docx` и журналы находятся в соседней папке `КТ6`, вне Git.

## КТ-7 — гибридное тестирование

Верхняя и нижняя части проверяются независимо и соединяются через `OrderService`.
`HybridOrderCases` задаёт одинаковые входные данные и ожидаемые результаты для
обеих частей и для полной цепочки. Верхняя часть проверяет контракт API с заменённым
сервисом, нижняя — настоящий репозиторий и схему H2 с тестовым драйвером.

| Этап | Настоящие компоненты | Точка входа и замены | Набор |
| --- | --- | --- | --- |
| Верхняя часть | MVC, контроллер, DTO, валидация, обработчик ошибок | MockMvc; `OrderService` заменён Mockito | `HybridApiContractTest`, 4 проверки |
| Нижняя часть | JDBC-репозиторий и H2 | Прямые вызовы из JUnit; верхние слои отсутствуют | `HybridStorageContractTest`, 3 проверки |
| Соединение | Весь orders: HTTP API, сервис, репозиторий, H2 и HTTP-клиент | Настоящие сетевые запросы; только users заменён HTTP-сервером | `HybridOrderFlowTest`, 7 проверок |
| Полная система | Оба приложения в отдельных JVM с собственными H2 | Существующие межсервисные тесты, включая управляемые отказы | `ServiceApiIT` и `UserServiceFailureIT`, 12 проверок |

Два общих набора данных проверяют цену `0.01` при количестве `1` и цену
`99999999.99` при количестве `1000`. Проверяются точная сумма `99999999990.00`,
Unicode, апостроф в названии товара и удаление пробелов по краям.
Ожидаемые суммы заданы явно и не вычисляются проверяемым методом.

Соединённые слои проверяются с двух сторон: POST создаёт запись, которую подтверждает
прямой SELECT; отдельная SQL-вставка затем читается через GET. Невалидная цена,
HTTP 404/500 от users и тайм-аут не должны добавлять строки или менять существующий
заказ. При задержке users 1500 мс и тайм-ауте клиента 400 мс проверяется ответ 503
раньше 1200 мс и неизменность БД до и после завершения попытки запоздавшего ответа.

Запуск этапов из корня репозитория:

```powershell
mvn -pl order-service -Dtest=HybridApiContractTest test
mvn -pl order-service -Dtest=HybridStorageContractTest test
mvn -pl order-service -Dtest=HybridOrderFlowTest test
mvn clean verify
```

В IDEA три класса запускаются зелёной кнопкой. Сервисы вручную запускать не нужно.
Нижняя часть получает отдельную H2 на каждый тест. В соединённой части таблица
очищается перед тестом, HTTP-серверы используют свободные порты и закрываются
после класса. Тестовые транзакции с откатом не используются.
Общие помощники `OrderDatabase` и `UserApiStub` находятся в `order.support`
и используются наборами КТ-6 и КТ-7.

В КТ-5 слои добавлялись сверху вниз, в КТ-6 — снизу вверх. В КТ-7 две части
имеют самостоятельные проверки общего контракта и сходятся на бизнес-сервисе.
Это позволяет отличать ошибки API или хранения от ошибок соединения слоёв.
Порядок выполнения отдельных методов JUnit для этого не задаётся.

КТ-7 добавляет 14 проверок. Итоговая сборка повторяет 45 тестов предыдущих КТ:
всего 59 успешных проверок. Новых дефектов приложения не обнаружено.
H2 и управляемые ответы users ограничивают промежуточные этапы; полная цепочка
с настоящим users проверяется в `verify`. Нагрузка и внешняя промышленная БД
в эту работу не входят. Отчёт `КТ7_Отчет.docx` и журналы находятся в соседней
папке `КТ7`, вне Git.

## Запуск приложений

Запустить классы `UserServiceApplication` и `OrderServiceApplication` как Java-приложения.
Либо после сборки выполнить в двух терминалах из корня репозитория:

```powershell
& 'C:\Program Files\Java\jdk-25\bin\java.exe' -jar user-service/target/user-service-0.0.1-SNAPSHOT.jar
```

```powershell
& 'C:\Program Files\Java\jdk-25\bin\java.exe' -jar order-service/target/order-service-0.0.1-SNAPSHOT.jar
```

Users слушает `http://127.0.0.1:18081`, orders — `http://127.0.0.1:18082`.

После перезапуска сервиса его данные теряются: H2 работает в памяти.

## HTTP API

| Сервис | Запрос | Ответ |
| --- | --- | --- |
| users | `POST /users` | 201, пользователь и Location |
| users | `GET /users/{id}` | 200, пользователь |
| orders | `POST /orders` | 201, заказ с пользователем и Location |
| orders | `GET /orders/{id}` | 200, заказ с пользователем |

Пользователь: `name` — непустая строка до 100 символов; `email` — email до 254 символов.

Заказ: `userId` — UUID; `product` — непустая строка до 200 символов;
`quantity` — целое число от 1 до 1000; `unitPrice` — от 0.01 до 99999999.99,
не более двух знаков после точки. Сумма `total` вычисляется через `BigDecimal`.
Заказ содержит один товар. Имя, email и название товара очищаются от пробелов по краям.

Проверка пользователя выполняется до сохранения заказа.
Ошибки возвращаются как `application/problem+json` с полями `status`, `detail`, `code`:

| HTTP | Код | Причина |
| --- | --- | --- |
| 400 | `INVALID_REQUEST` | Невалидные поля, JSON или UUID |
| 404 | `USER_NOT_FOUND` / `ORDER_NOT_FOUND` | Ресурс не найден |
| 422 | `USER_NOT_FOUND` | Пользователь для нового заказа отсутствует |
| 503 | `USER_SERVICE_UNAVAILABLE` | Ошибка соединения, тайм-аут или некорректный ответ users |

## Настройки

| Переменная окружения | По умолчанию |
| --- | --- |
| `USER_SERVICE_PORT` | `18081` |
| `ORDER_SERVICE_PORT` | `18082` |
| `USER_SERVICE_URL` | `http://127.0.0.1:18081` |
| `USER_SERVICE_CONNECT_TIMEOUT` | `1s` |
| `USER_SERVICE_READ_TIMEOUT` | `2s` |

При смене порта users нужно изменить `USER_SERVICE_URL` в orders.
Тайм-ауты должны быть положительными; автоматических повторов нет.
Измерения тестов относятся к локальным последовательным запросам, а не к нагрузочному тесту.
