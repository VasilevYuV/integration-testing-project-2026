# КТ-4 — интеграционное тестирование eShopOnWeb

Отдельный стенд для проверки интернет-магазина методом «большого взрыва».
До выполнения сценариев соединяются Web, PublicApi, бизнес-логика, репозитории
и SQL Server. Подготовка БД выполняется до старта Web, чтобы два приложения
не применяли одни миграции одновременно. Это порядок запуска инфраструктуры,
а не поэтапная замена компонентов заглушками.

## Исходный проект

Используется [dotnet-architecture/eShopOnWeb](https://github.com/dotnet-architecture/eShopOnWeb)
из задания, ревизия `4da8212117e87d808d4bbc7da6286fd2147ce606`, лицензия MIT.
Исходники загружаются в `.upstream/` и не включаются в этот репозиторий.
`upstream.lock.json` закрепляет commit и digest образов SDK, ASP.NET Core и SQL Server.
Лицензия исходного приложения сохраняется внутри собранных образов.

| Компонент исходного проекта | Назначение и связи |
| --- | --- |
| Web | Razor Pages и MVC, каталог, корзина, оформление и просмотр заказов |
| ApplicationCore | Модели каталога, корзины и заказов, бизнес-сервисы и контракты репозиториев |
| Infrastructure | EF Core, SQL Server, реализация репозиториев, ASP.NET Core Identity |
| PublicApi | HTTP API каталога и авторизации для административного интерфейса |
| BlazorAdmin и BlazorShared | Административный интерфейс, клиент API и общие DTO |
| SQL Server | Две базы: `KT4Catalog` для каталога и заказов, `KT4Identity` для пользователей |

Область КТ-4 — приложение eShopOnWeb. Правила вымышленного магазина из КТ-3,
включая PayPal, SAVE10 и почтовую доставку, не переносятся на него автоматически.

## Структура

```text
eshop-big-bang/
├── compose.yaml
├── Dockerfile
├── Dockerfile.tests
├── compose.tests.yaml        # временный стенд без опубликованных портов
├── upstream.lock.json
├── environment/              # настройки учебного стенда
├── scripts/                  # подготовка, запуск, проверка и остановка
├── tests/BigBangTests/        # HTTP-тесты по модулям магазина
├── .upstream/                # загруженный оригинал, вне Git
├── .env                      # локальный пароль и образы, вне Git
└── artifacts/                # результаты запусков, вне Git
```

`environment/global.json` заменяет `8.0.x` из upstream конкретной минимальной
версией SDK с переходом на установленный feature band .NET 8. Подмена выполняется
только внутри Docker-сборки. Исходный Git checkout остаётся чистым.

Браузер обращается к API через `localhost:18302`, а контейнер Web — через
`api:8080`. Отдельный `appsettings.Docker.json` задаёт адреса браузерного Blazor-клиента.
Порты Java-сервисов КТ-2 остаются 18081 и 18082.

## Запуск

Нужны Git, PowerShell 7 и Docker Desktop с Linux containers. Локальный .NET SDK
для контейнерной сборки не требуется. Первый запуск скачивает зависимости.

Из этой папки:

```powershell
./scripts/Start-Environment.ps1
```

Команда загружает закреплённую ревизию, создаёт `.env`, собирает приложения,
поднимает SQL Server и API, затем Web и проверяет доступность компонентов.
Случайный пароль БД хранится только в `.env`; SQL Server не публикует порт на хосте.
Web и API доступны только на локальном компьютере.

- Магазин: http://localhost:18301/
- Административная часть: http://localhost:18301/admin
- Swagger: http://localhost:18302/swagger/
- Состояние Web и его связей: http://localhost:18301/health

Учебные пользователи исходного проекта: `demouser@microsoft.com` и
`admin@microsoft.com`, пароль `Pass@word1`. Эти опубликованные демонстрационные
данные предназначены для локального стенда.

## Проверка и остановка

```powershell
./scripts/Test-Environment.ps1
docker compose ps
docker compose logs --tail 80 web api
./scripts/Stop-Environment.ps1
```

`Test-Environment.ps1` проверяет каталог в Web и API, `/health`, Swagger и адрес
API в конфигурации браузера. Результат записывается в
`artifacts/environment-check.json`. Это проверка готовности стенда.

В контейнере Web используется тот же порт 18301, что и на хосте: штатная проверка
главной страницы строит URL из входящего HTTP-заголовка Host и вызывает его из Web.

Остановка сохраняет базы в томе `kt4-eshop_database`. Повторный запуск использует
те же данные. Для проверки на пустой БД можно запустить отдельный Compose-проект
с новым именем, предварительно остановив этот стенд для освобождения портов.

Отчёт КТ-4 в формате DOCX и доказательства выполнения хранятся в соседней папке
`КТ4/`, вне Git.

## Полный набор КТ-4

```powershell
./scripts/Run-BigBangTests.ps1
```

Команда собирает приложения и тесты, создаёт отдельный Compose-проект
`kt4-check-<случайный id>` с пустой SQL Server, запускает 16 тестов xUnit и
проверяет отключение/восстановление API. Временный стенд не публикует порты
и может работать одновременно с обычным `kt4-eshop`. После прогона его
контейнеры и том БД удаляются. Основной том `kt4-eshop_database` не затрагивается.
Нужен Docker Compose V2 с поддержкой `!reset`; проверено на 2.39.2-desktop.1.

Тесты вызывают реальные Web и API по HTTP, сохраняют cookies, получают antiforgery
токены из форм и проверяют сохранённые данные повторными запросами, в том числе
после входа в новом сеансе. Контроллеры, бизнес-сервисы, репозитории и SQL Server
работают вместе. TestServer, EF InMemory и моки в собственном наборе не используются.
Штатные тесты upstream не входят в эти 16 и отдельно не запускались.

| Модуль | Проверки |
| --- | --- |
| `Catalog` | CAT01–03: пагинация Web/API, фильтры бренда/типа, отсутствующий товар |
| `Basket` | BAS01–05: повторное добавление, количество и удаление, защита цены, изоляция одновременных сеансов, валидация и antiforgery |
| `Identity` | AUTH01–02: перенос гостевой корзины при входе, новый сеанс, запрет гостевого оформления и неверный пароль |
| `Orders` | ORD01–03: сохранение заказа и суммы, очистка корзины, пустой заказ, доступ другого пользователя |
| `Administration` | API01–03: CRUD через JWT администратора, 401/403 для остальных, конфликт дубликата 409 |
| `Support` | HTTP-сеанс и чтение форм закреплённой версии приложения |

Сценарии используют независимые cookies и уникальные учётные записи; временный
товар удаляется в `finally`. Сценарии исполняются последовательно из-за общего
каталога и кеша. BAS03 дополнительно выполняет два добавления конкурентно.

Артефакты записываются в `artifacts/<дата-время>/`:

- `big-bang.trx` — исходный протокол xUnit/VSTest;
- `summary.json` — результат и HTTP-трасса каждого теста;
- `test-output.log`, `services.log` — вывод тестов и приложений;
- `run.json` — ревизия eShopOnWeb, базовый коммит стенда, SHA-256 файлов тестов;
- `api-outage.json`, `health-api-down.json`, `health-recovered.json` — управляемый сбой.

JWT, пароли и cookies не записываются в HTTP-трассу тестов. `artifacts/`, `.env`,
`.upstream/` и локальные `docs/` исключены из коммита.

## Результат 30 октября 2026 года

Итоговый прогон `20261030-131437`: **16 тестов, 14 Passed, 2 Failed**, пропусков нет.
Падения воспроизводят два дефекта исходной ревизии:

| Дефект | Сценарий | Наблюдение и причина |
| --- | --- | --- |
| D01, высокий приоритет | ORD03 | Другой пользователь читает чужой заказ по ID с HTTP 200. `GetOrderDetailsHandler` выбирает заказ по ID без проверки `request.UserName`/`BuyerId`. |
| D02, средний приоритет | BAS04 | Прямой POST количества `-1` возвращает «Basket is empty» без ошибки валидации. БД сохраняет прежнее количество. `OnPostUpdate` возвращается до загрузки `BasketModel`; Razor выводит ошибки только внутри непустой корзины. |

Оба дефекта также воспроизведены в Chrome. Для D02 прямой POST обходит браузерное
ограничение `min=0`. Обычный ввод через форму дополнительно защищён браузером;
дефект относится к ответу серверной валидации.

**Код возврата 1 — фактическое падение двух проверок.** Проверки не пропущены
и не заменены ожиданием ошибочного поведения. Исходники eShopOnWeb не исправлялись.
КТ завершена регистрацией дефектов; это не означает отсутствия ошибок в приложении.

При управляемом отключении API `/health` вернул 503 и `api_health_check=Unhealthy`,
а каталог Web вернул 200. Web читает каталог через собственный SQL-репозиторий,
поэтому результат соответствует архитектуре. После запуска API `/health` снова
вернул 200/Healthy. Это отдельный эксперимент, не третий дефект.

Оформление создаёт заказ с фиксированным адресом; платёжный шлюз не вызывается,
почтовый сервис исходного проекта не отправляет письма. Административные операции
проверяются через API. Полный прогон Blazor, нагрузочные испытания и аудит всех
уязвимостей не выполнялись.
